# 第一阶段：梳理现有商城项目结构

## 1. 阶段目标
- 建立当前项目的完整结构认知，明确可复用模块、需要改造模块、可下线模块。
- 确认外卖点单最小可行链路（浏览菜品 -> 点单车 -> 下单 -> 支付 -> 订单查询）的现状可达性。
- 输出可执行改造清单与风险清单，作为后续阶段输入。

## 2. 开发内容
- 梳理页面路由、Tab 结构、页面之间跳转关系。
- 梳理服务层接口：商品、购物车、订单、支付、地址、活动、优惠等。
- 梳理数据模型：订单、订单项、购物车项、商品与 SKU、地址等。
- 梳理支付调用链与订单状态流转点。
- 识别与外卖目标无关的复杂商城能力入口。

## 3. 涉及模块
- 全局配置：app.json、custom-tab-bar
- 页面：pages/home、pages/goods、pages/cart、pages/order、pages/usercenter
- 服务：services/good、services/cart、services/order、services/pay、services/coupon、services/promotion
- 模型：model/good、model/cart、model/order、config/model.js

## 4. 详细任务步骤
1. 产出路由与页面职责清单
- 列出主路径页面、子页面和入口来源。
- 标注每个页面在目标外卖流程中的角色。

2. 产出业务链路图
- 画出从菜品浏览到支付成功的调用链。
- 明确关键函数触发点和状态更新点。

3. 产出复用分类表
- 分为可复用、需改造、可隐藏、可删除四类。
- 每条分类附原因与影响范围。

4. 产出风险矩阵
- 标记高风险改动点（订单状态、支付、库存、地址）。
- 为每个风险补充规避策略与回滚建议。

5. 评审并冻结基线
- 组织一次技术评审确认改造边界。
- 冻结本阶段结果作为后续开发基线。

## 5. 测试重点
- 现网主链路可用性验证。
- 页面入口完整性与路由可达性验证。
- 下单与支付最小闭环可复现性验证。

## 6. 注意事项
- 禁止在本阶段进行功能改造，只做事实梳理与风险识别。
- 术语统一使用目标命名：商品=菜品、购物车=点单车（仅文档语义）。
- 评审结论必须记录为明确动作，不保留模糊项。

## 7. 交付物
- 项目结构盘点文档
- 功能复用分类表
- 高风险模块矩阵
- 改造边界确认单

## 8. 完成标准
- 所有后续阶段都能以本阶段交付物直接开工。
- 不再出现核心模块职责不清导致的返工。
